# ADR-010: Lambda Code and Alias Ownership

## Status

Accepted

## Context

The Lambda Terraform module currently declares the deployment package, publishes a
version, and points an alias at that version. The delivery workflow also updates
function code, publishes versions, and moves the staging and production aliases
directly through AWS APIs. These two writers can disagree: after a successful CD
promotion, a later Terraform apply can attempt to restore the version recorded in
Terraform state.

PR previews behave differently. Their Terraform state is isolated per PR, and the
preview workflow creates the infrastructure and deploys the candidate package in
one apply. Treating previews like long-lived environments would add a second
deployment mechanism without reducing drift risk.

This ADR assigns exactly one writer for Lambda function code and alias targets in
each environment. It clarifies ADR-009; it does not change runtime behavior.

## Decision

Use an environment-scoped ownership model:

| Environment | Function code and published versions | Alias target | Infrastructure and runtime configuration |
|---|---|---|---|
| PR preview | Terraform is the only writer. | Terraform is the only writer. | Terraform. |
| Staging | GitHub Actions CD is the only writer after bootstrap. | GitHub Actions CD is the only writer after bootstrap. | Terraform. |
| Production | GitHub Actions CD is the only writer after bootstrap. | GitHub Actions CD is the only writer after bootstrap. | Terraform. |

"After bootstrap" means Terraform may create a long-lived function and its alias
with an initial package. Once they exist, Terraform must not publish application
versions or move the alias. All subsequent application delivery and rollback for
staging and production belongs to CD.

### Why this model

| Alternative | Result |
|---|---|
| Terraform owns delivery everywhere | Rejected. The current staging and production workflow already performs package-hash validation, staged promotion, smoke checks, previous-version capture, and alias rollback. Rebuilding those release semantics around Terraform would make an infrastructure apply the application release operation. |
| CD owns delivery everywhere | Rejected. A preview is created from isolated Terraform state and destroyed with that state. Splitting preview creation from its first code deployment adds coordination and cleanup failure modes. |
| Terraform and CD both update long-lived aliases | Rejected. Two writers make the most recent command, rather than an auditable policy, the effective source of truth. |
| Environment-scoped ownership | Accepted. It matches current workflow boundaries while removing competing writers for each Lambda resource instance. |

The ownership boundary is the important invariant: an environment must never
switch writers implicitly because a command happens to have permissions.

## Terraform lifecycle contract

The Terraform implementation must expose the ownership mode explicitly rather
than rely on operator convention.

For **staging and production**:

- Terraform continues to own the function identity, IAM, runtime, handler,
  memory, timeout, environment variables, tags, logging, API Gateway integration,
  and alias identity.
- Terraform must ignore remote application-delivery changes: function package
  content/version and alias target version. Alias descriptions that CD uses for
  release metadata must also be outside Terraform reconciliation.
- A normal plan or apply must not publish a Lambda version, move an alias, or undo
  a CD rollback.
- Changing infrastructure-owned function configuration remains a Terraform
  change. Any version publication caused by provider behavior must not move the
  traffic alias; CD must perform the next promotion.
- Bootstrap is a separately identified operation. It is not a supported path for
  routine releases.

For **PR previews**:

- Terraform must continue to detect package changes and reconcile the function
  version and alias target in the isolated preview state.
- Preview apply and destroy remain the complete resource lifecycle. CD must not
  move preview aliases out of band.

Lifecycle ignores deliberately remove application delivery from Terraform drift
management; they do not declare that drift is acceptable or invisible.

## CD promotion and rollback contract

GitHub Actions owns long-lived application delivery and must:

1. Build one immutable package and record its SHA-256 digest.
2. Verify that digest before each deployment.
3. Publish a new Lambda version; never deploy mutable unpublished code to a
   traffic alias.
4. Move only the alias for the target environment after its required gates pass.
5. Record the function name, environment, commit SHA, package digest, published
   version, previous alias version, workflow run, and actor as deployment evidence.
6. Promote production from the same validated package digest used by the staging
   gate; rebuilding is not promotion.
7. Capture the production alias target before promotion and use that immutable
   version as the automatic rollback target.
8. Roll back by moving the alias only. Rollback must not mutate Terraform state or
   publish a replacement package.

The automatic rollback path owns failures from the production smoke check. A
manual rollback must require an explicit published target version and produce the
same evidence as promotion. Terraform operators are not responsible for choosing
or applying application rollback targets.

## Drift detection and reconciliation

Drift is evaluated against the owner of each field:

| Drift class | Detection | Reconciliation owner and action |
|---|---|---|
| Infrastructure or runtime configuration | Scheduled and pull-request Terraform plans. | Terraform changes or imports the resource after review. |
| Long-lived function code or alias target | A scheduled deployment audit compares AWS function/alias state with the latest successful CD deployment evidence. | CD re-promotes the recorded immutable version, performs an explicit rollback, or records the observed version as a reviewed break-glass deployment. Terraform apply is forbidden as a repair. |
| Preview code or alias target | Terraform plan in the PR preview state, plus preview smoke output. | Reapply or destroy the preview through its Terraform workflow. Out-of-band alias moves are overwritten. |
| Missing or ambiguous deployment evidence | Audit fails closed and blocks the next promotion. | A maintainer identifies the deployed package/version and records a reviewed reconciliation before delivery resumes. |

A Terraform plan that is clean is not proof that staging or production code is
correct, because delivery-owned fields are intentionally ignored. Conversely, an
application drift alert must not authorize Terraform to move an alias.

Emergency console or CLI changes are break-glass operations. They require a
reason and actor, and must be reconciled through CD evidence. If the version is not
approved, CD restores an approved immutable version; if it is approved, the
deployment ledger is updated through a reviewed reconciliation procedure.

## Environment consequences

### PR preview

- The package remains an input to Terraform, so the preview represents the PR's
  infrastructure and code in one isolated state.
- Reapplying the preview can replace its version and alias target.
- Destroying the preview removes the environment without consulting a long-lived
  deployment ledger.

### Staging

- Terraform provisions and configures the durable environment but does not
  deliver later application versions.
- CD publishes the candidate and moves the staging alias before smoke and
  evaluation checks.
- A failed staging validation blocks production; it does not trigger a Terraform
  apply as recovery.

### Production

- Only the gated main-branch CD path promotes the validated package to the
  production alias.
- Production smoke failure restores the previously captured alias version.
- Terraform plans remain useful for infrastructure drift but cannot report or
  repair code/alias drift.

## Consequences

### Positive

- Every Lambda code revision and alias target has one authoritative writer.
- Terraform cannot silently undo a successful promotion or rollback.
- Release evidence and rollback semantics stay in the delivery workflow that
  already validates immutable packages.
- Preview environments remain simple and self-contained.

### Negative

- Drift detection requires both Terraform plans and a deployment-specific audit.
- The Terraform module needs an explicit ownership mode and environment-specific
  lifecycle behavior.
- Infrastructure configuration changes that publish a version require care:
  publishing alone does not put that version into service.
- Break-glass changes create an evidence-reconciliation obligation.

## Follow-up implementation issues

The following work is required to implement this decision. These are issue
descriptions, not work included in this ADR:

1. **Add explicit Lambda delivery ownership to Terraform.** Introduce a validated
   module input, configure lifecycle behavior for CD-owned staging/production, and
   retain Terraform ownership for previews. Add plan-level tests proving that a
   long-lived apply cannot move an alias after CD promotion.
2. **Persist immutable Lambda deployment evidence.** Extend the workflow to record
   the package digest, published and previous versions, commit, run, environment,
   and actor for promotion and rollback.
3. **Audit Lambda delivery drift.** Add a scheduled/read-only check that compares
   AWS function and alias state with the latest successful deployment evidence and
   fails closed when evidence is missing or ambiguous.
4. **Define break-glass reconciliation.** Document and automate the reviewed paths
   for restoring an approved version or adopting an explicitly approved emergency
   deployment without using Terraform as the repair tool.
5. **Verify preview ownership boundaries.** Add workflow tests proving preview
   code and aliases are Terraform-owned and cannot reuse long-lived deployment
   commands.

## Out of scope

- Lambda runtime or application behavior changes.
- Frontend or admin hosting decisions.
- Live AWS deployment or Terraform apply.
- Creation of the follow-up GitHub issues listed above.
